# Multi-page PAGE / NUMPAGES / PAGEREF field behaviour

Empirically measured behaviour of page-number fields on a **multi-page** document across
Microsoft Word, WPS Writer, and LibreOffice Writer. This is a **facts** file, not product
guidance. It resolves the open research item in spec `docs/spec/v0.1.md` §D8 / Further Notes
("whether a footer `PAGE`/`NUMPAGES` field displays the correct number per page without a
manual update on a multi-page document — current evidence covers single-page cases only").

Issue: [#3](https://github.com/loststarry09/wordflow/issues/3). Instrument: the #2 harness
(`scripts/wf-compat-harness.sh`, documented in `references/compatibility/harness.md`).

Legend:

- **[V]** — verified by running the tools locally (versions below).
- **[S]** — backed by OOXML / ECMA-376 or another primary source.
- **[?]** — reported elsewhere but not confirmed here; treat as uncertain.

## Versions

OfficeCLI `1.0.152`; Microsoft Word `16.0` (Office 16); WPS Writer `12.0`; LibreOffice
`24.2.7.2`. Word and WPS driven read-only over COM (WSL interop); LibreOffice headless with an
isolated profile. Measured 2026-10-01.

## The question

Single-page evidence cannot distinguish a **correct per-page value** from a **frozen cached
value**, because on a one-page document both are `1`. This study forces a document with a known
true page number for every element, seeds a *stale* cache, and asks what each application
actually displays.

## Fixture

`tests/fixtures/multipage/page-fields.docx` (generated by `tests/generate-fixtures.sh`):

- **Exactly 4 pages**, forced by three explicit `w:br w:type="page"` breaks rather than by
  overflowing text, so the true page of every paragraph is deterministic in every application.
  Page 1: title + `Heading1 "Section One"`; page 2: `Heading1 "Section Two"`; page 3:
  `Heading1 "Section Three"` + a bookmark `target`; page 4: `Heading1 "Section Four"` + a body
  `PAGEREF target`. A `TOC \o "1-2"` with page numbers lists the four headings.
- **Footer** is `"Page " + PAGE + " of " + NUMPAGES`, centred.
- **Cached values written by OfficeCLI** (`officecli query <fixture> field`): `PAGE = 1`,
  `NUMPAGES = 1`, body `PAGEREF target = 1`, TOC-entry `PAGEREF`s `1,2,3,4`. The file carries no
  `w:updateFields`.
- `officecli validate` passes; no placeholder caches.

True values: page 1 shows page number **1**; the last page shows **4**; `NUMPAGES` is **4**;
the body `PAGEREF target` refers to a bookmark on page **3**.

## What each application displays (no F9)

Measured from each application's own PDF export, read per page with `pdftotext -f N -l N`
(the harness exports these; the PDF is the application's own pagination and footer rendering).

| Application | Page 1 footer | Last page (4) footer | Matches true number? | Body `PAGEREF` on page 4 |
|---|---|---|---|---|
| Word 16.0 | `Page 1 of 4` | `Page 4 of 4` | **Yes** | `... on page 3` (correct) |
| WPS Writer 12.0 | `Page 1 of 4` | `Page 4 of 4` | **Yes** | `... on page 3` (correct) |
| LibreOffice 24.2.7.2 | `Page 1 of 4` | `Page 4 of 4` | **Yes** | `... on page 3` (correct) |

- **[V]** All three applications show the correct page number and the correct total on every
  page, with **no F9 / Update Field** action. The stale cache (`1` / `1`) is never displayed.
- **[V]** All three applications also show the correct target page (`3`) in the body `PAGEREF`,
  although its cached value is `1`.

## Why: the cache is not what is displayed (proof by field lock)

`w:fldLock` (exposed by OfficeCLI as `--prop fldLock=true`) tells Word **not** to update the
field on F9 / Update Field; the cached result is meant to stay put. Two control probes:

**Probe A — locked `PAGE` / `NUMPAGES` (`mp_lock`, 3 pages, cache pinned to `1`).**

- Word object model: `PAGE = 1`, `NUMPAGES = 3`.
- WPS object model: `PAGE = 1`, `NUMPAGES = 1`.
- **Rendered PDFs (all three):** `Page 1 of 3`, `Page 2 of 3`, `Page 3 of 3`.

- **[V] The per-page number cannot be coming from the cache**, because the cache is locked at
  `1` and all three still render `2` and `3` on the later pages. The page number is computed by
  the layout engine as each page is paginated/rendered. This is true even for `NUMPAGES`.
- **[V]** The live object-model field result is **not** the displayed value for page fields:
  WPS reported `NUMPAGES = 1` while displaying `of 3`; Word reported `PAGE = 1` while displaying
  `2`/`3` on pages 2/3. Reading field results through COM is therefore unreliable for these
  fields.

**Probe B — locked body `PAGEREF` (`mp_lockref`, 3 pages, bookmark on page 2, cache `1`).**

| Application | Body `PAGEREF` displayed on page 3 | Correct? |
|---|---|---|
| Word 16.0 | `on page 1` | **No** (true: 2) |
| WPS Writer 12.0 | `on page 1` | **No** (true: 2) |
| LibreOffice 24.2.7.2 | `on page 2` | Yes |

- **[V]** With the field locked, Word and WPS display the **stale cached value** for `PAGEREF`;
  LibreOffice ignores `fldLock` and recomputes.
- **[V]** Combined with the unlocked run (body `PAGEREF` correct in all three), this shows
  Word/WPS *do* update an **unlocked** `PAGEREF` during rendering/export, but honour `fldLock`;
  LibreOffice always recomputes `PAGEREF`. The distinction between the stored cache and the
  rendered value is what the prior single-page evidence could not expose.
- **[?]** Whether Word/WPS refresh an unlocked `PAGEREF` on screen (before print/export) as
  opposed to only in the export/print path could not be separated here: the live object-model
  result stayed `1` even after `Document.Repaginate()` and `ComputeStatistics(pages)`, while the
  exported render showed `3`. For `PAGE`/`NUMPAGES` this question does not arise — they are
  layout values and render correctly in any paginated view.

## Table of contents page numbers

- **[V]** The fixture's TOC cached page numbers (`1,2,3,4`) happen to equal the true pages, so
  this run does not by itself distinguish recompute from cache.
- **[V]** (prior evidence, re-affirmed) OfficeCLI's `refresh` fills the TOC from its **HTML
  pagination**, which does not match Word/WPS layout; a mismatched cached value is displayed
  verbatim by Word, WPS, and LibreOffice because none rebuilds the TOC on open. See
  `field-recalc-and-cross-app-verification.md` §2–§3, §6. The frozen decision to ship the TOC
  **without page numbers** (spec §D9) is unaffected.

## Conclusion

**Footer page numbers (`PAGE` + `NUMPAGES`) are safe to ship in v0.1.**

- **[V]** On a forced 4-page document, Word 16.0, WPS 12.0, and LibreOffice 24.2.7.2 each display
  the correct number on page 1 **and** the last page, and the correct `NUMPAGES`, without any
  manual field update — even though the document's cached `PAGE`/`NUMPAGES` values are `1`.
- **[V]** The correct value is produced by layout, independent of the cached result (proved by
  locked fields). WordFlow therefore does not need to compute or guarantee a page number for
  `PAGE`/`NUMPAGES`; the reader's application always does.
- No downgrade is required for a footer `PAGE`/`NUMPAGES` on a single-section, continuous-numbering
  document. (Page-number **restart** and different-first-page/odd-even headers remain separate,
  still-limited items — specs §D9.)

**Page-number cross-references (`PAGEREF`) and TOC page numbers remain limited/omitted.**

- `PAGEREF` renders correctly in all three when unlocked, but Word/WPS depend on a render-time
  update and honour `fldLock`; the stored cache is stale. WordFlow cannot write a *correct*
  cached page number (it has no layout engine), so per §D9/§D11 it must not present one it
  cannot guarantee: keep `see page N` as a **limited** capability and downgrade to a content
  reference where possible. The TOC stays without page numbers (§D9, frozen).
- Because `PAGE`/`NUMPAGES` are layout fields while TOC/REF/SEQ are cached-text fields, the
  report/QA vocabulary should separate them: a stale cached `PAGE`/`NUMPAGES` is **not** a
  defect, whereas a placeholder or wrong cached TOC/REF remains one (§D11, §D14).

## Spec / documentation conflicts raised by this evidence

1. **`PROJECT_STATUS.md` §5** and `references/research/field-recalc-and-cross-app-verification.md`
   (§3–§4) state: *"no application updates fields on its own. The cached result **is** what the
   reader sees."* This is **not true for page-dependent fields**. `PAGE`/`NUMPAGES` are computed
   by every application from the current layout, and an unlocked `PAGEREF` is rendered with a
   recomputed page number. The earlier conclusion was drawn from the COM field result
   (the *stored cache*), which for page fields is not what is displayed.
2. **Spec §D8** declares the multi-page page-number behaviour *unverified*; this study verifies
   it positively. D8 and the Further Notes open item should be updated (no downgrade needed for
   footer page numbers).
3. **Spec §D14** ("no field is judged … on flags alone — a field is judged by its **cached
   text**") needs a carve-out: for `PAGE`/`NUMPAGES` the cached text is legitimately stale and
   the display is nevertheless correct; the cached-text rule still governs TOC/REF/SEQ.
4. **`references/compatibility/harness.md`** says the LibreOffice `render.pdf` *"shows the cached
   result as rendered"* and that `app_field_cache` *"records what that application will actually
   display"*. Both are wrong for page-dependent fields: LibreOffice recomputes
   `PAGE`/`NUMPAGES`/`PAGEREF`; the Word/WPS object-model result for `PAGE` stays `1` while the
   display is per-page. Per-application **PDF text** is the reliable display signal for these
   fields.
5. **Spec §D9** states *"Page-number fields generally follow the same principle: WordFlow never
   presents a page number it cannot guarantee."* For footer `PAGE`/`NUMPAGES` the guarantee comes
   from the reader, not from WordFlow; this sentence should be scoped to page-number
   *cross-references* and TOC entries.

## Reproduction

```sh
# regenerate the fixture (also regenerates every other fixture)
tests/generate-fixtures.sh

# all three applications, under the shared COM lock (Word/WPS)
flock -w 1800 /tmp/wordflow-wincom.lock \
  scripts/wf-compat-harness.sh tests/fixtures/multipage/page-fields.docx \
  --apps word,wps,libreoffice --out tests/.out/compat/issue3 --no-visual

# read what each application displays per page
for app in word wps libreoffice; do
  pdf=tests/.out/compat/issue3/tests_fixtures_multipage_page-fields_docx/$app.pdf
  n=$(pdfinfo "$pdf" | awk '/^Pages/{print $2}')
  for p in $(seq 1 "$n"); do echo "--- $app page $p ---"; pdftotext -f "$p" -l "$p" "$pdf" -; done
done
```
